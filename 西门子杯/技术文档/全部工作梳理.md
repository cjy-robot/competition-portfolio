## 第一章：起点

### 我们要做什么

目标：在 GD32H759IMK6 MCU 上部署完整的车牌检测+识别系统。

```
OV2640 拍照 → 缩放到 192×192 → YOLO 检测车牌位置
→ 原图裁剪车牌 → 灰度 94×24 → LPRNet 识别 → 输出 7 位车牌号
```

### 硬件约束

| 资源 | 容量 | 挑战 |
|------|------|------|
| Flash | 2MB | 两个 AI 模型 + 代码 + 权重 |
| SRAM | 1MB | 相机帧缓冲 960KB + YOLO 输入 432KB → **超过 1MB** |
| CPU | Cortex-M7@600MHz | 推理必须 <500ms |

### 已有的东西

- PyTorch 训练好的 YOLO-FastestV2（`plate_best_120.onnx`，238K 参数，mAP 0.998）
- PyTorch 训练好的 LPRNet Tiny（`lprnet_tiny_best.pth`，105K 参数）
- GD32 Keil 工程，里面有个 `plate-best-sim.tflite`，但效果不好
- CCPD2019 数据集，20 万+ 中国车牌，8 个类别

### 已有模型参数卡片

## 第二章：理解现有模型

### 第一步：搞清楚 plate_best_120.onnx 到底输出了什么

用 ONNX Runtime 加载模型，仔细分析：
- 输入：`[1, 3, 192, 192]` NCHW float32
- 输出 0：`[1, 12, 12, 16]`，stride=16
- 输出 1：`[1, 6, 6, 16]`，stride=32

16 通道 = 3 个 anchor × 4 个 reg(tx,ty,tw,th) + 3 个 obj + 1 个共享 cls。

**关键发现**：输出已经过 sigmoid！`export_onnx=True` 让模型在导出之前自动做了 sigmoid。这意味着 decode 时不能再做 sigmoid。

### 第二步：写出正确的解码公式

```
cx = (tx*2 - 0.5 + gx) * stride    ← tx∈[0,1]，允许偏移 ±0.5 格
cy = (ty*2 - 0.5 + gy) * stride
bw = (tw*2)² * anchor_w             ← tw∈[0,1]，允许缩放 0~4×
bh = (th*2)² * anchor_h
conf = obj * cls
```

### 第三步：K-means 重新计算 Anchors

原来 GD32 模型用的 anchors 是 `[47.30,10.52]...[99.27,21.31]`（6 个，来自不知名数据）。

从 18000+ CCPD 标注框重新聚类计算，新的 6 个 anchors 平均 IoU 比原来高 6%：

```
Head0 (stride=16，小面积):  [31.24, 8.24]  [54.07, 13.34]  [49.55, 24.23]
Head1 (stride=32，大面积):  [77.18, 18.28]  [69.73, 35.59]  [114.20, 31.10]
```

### 第四步：分析 plate-best-sim.tflite 为什么不行

这个模型是 GD32 AI GUI 生成的。运行后发现和 ONNX 的 IoU=0——不是同一个模型架构！
- 只有 2 个 anchor/scale（不是 3 个）
- Anchors 值不同
- 输出还没过 sigmoid

而且配套的 C 解码代码 `yolo_postprocess.c` 有 4 个 bug：
1. 只解码 2 个 anchor（实际模型有 3 个）
2. Channel 读取方式错误（连续读 6 字节 vs 实际 reg[0-3]+obj[12-14]+cls[15]）
3. 对已经 sigmoid 过的值又做了一次 sigmoid（双倍 sigmoid）
4. Anchors 值用的是旧的，不匹配当前模型

**这就是 plate-best-sim 效果差的根本原因。**

## 第三章：LPRNet 训练与量化

### 第一步：准备 LPRNet 数据

写了 `prepare_lprnet_data.py`：
- 从 CCPD 文件名解析车牌号（编码在文件名中，如 `03AQK549_3_...`）
- 解析 ground truth 边界框
- 定义字符表 VOCAB：31 省份简称 + 34 字母数字（去掉 I 和 O）= 65 类
- CTC blank 索引 = 65，总类别 = 66

### 第二步：训练

写了 `lprnet_train.py`：
- 模型：LPRNetTiny（105K 参数）
- Dataset：在线从 CCPD 原图裁剪车牌区域（15% margin），转灰度，resize 94×24
- 数据增强：随机亮度、高斯噪声、模糊
- 损失函数：CrossEntropyLoss（位置分类）
- 优化器：Adam + CosineAnnealingLR
- 训练 50 epoch，保存最佳权重

### 第三步：量化前的惨烈 debug

将 PyTorch 模型迁移到 Keras 做 INT8 量化。迁移后输出和原始 PyTorch **差异高达 28.79**！

逐层对比（写了 `debug_layer_by_layer.py`），找到两个 root cause：
1. **Conv 权重没设置**：`model.get_layer('conv1_conv').set_weights([w])` 漏写了，这层用的是随机初始化的 Keras 默认权重
2. **BatchNormalization epsilon**：PyTorch 默认 1e-5，Keras 默认 1e-3，差了 100 倍

修复后：**Keras vs PyTorch 最大差异 0.000010**。

### 第四步：INT8 量化成功

LPRNet 没有 ShuffleNetV2 那种 channel shuffle，Keras→TFLite INT8 转换很顺利：
- 大小：**118KB**
- 精度：整牌 86%，字符级 98%
- 输入：`[1, 24, 94, 1]` int8, scale=0.003922, zp=-128
- 输出：`[1, 7, 66]` int8, scale=0.265244, zp=-18

### 第五步：PC 端验证

三个模型（PyTorch Float / TFLite Float32 / TFLite INT8）对同一张灰度图的输出**完全一致**。LPRNet 在 PC 端没问题。

## 第四章：YOLO 量化 — 漫长的探险

这是整个项目中最艰难的部分，走了无数弯路。

### 第一回合：ONNX Runtime QDQ 量化

用 ONNX Runtime 的 `quantize_static()` 做 QDQ 格式量化：
- 校准数据：200 张 CCPD 混合类别随机采样
- 量化配置：INT8 对称量化（per-tensor）

结果：**532KB，100% 精度，检测框偏差 <3px**。完美！

但问题是——这个模型是 ONNX 格式的，嵌入了 QuantizeLinear/DequantizeLinear 节点。GD32 MCU 需要的是 TFLite 格式。

### 第二回合：尝试 GD32 AI GUI 导入

用户尝试导入 `plate_best_120.onnx`（float32）到 GD32 AI GUI，报错 "Upload dir error"。

后来把 INT8 QDQ ONNX 喂给 GUI，报错：
```
IndexError: tuple index out of range
```
发生在 `DequantizeLinear` 节点处理 Conv bias [24] 时—QDQ 的 axis 参数无法正确广播到 1D tensor。

**GD32 AI GUI 底层用的就是 onnx2tf。onnx2tf 不认识 QDQ 节点。**

### 第三回合：onnx2tf 直接转 float32 ONNX

不用 QDQ，直接拿 float32 ONNX 让 onnx2tf 转 TFLite。

转换成功了（972KB float32 TFLite），但**精度全丢**——和 ONNX 对比 diff 高达 0.51。即使全零输入，差异也是 0.67。

检测实测：能出框，但偏差 20-40px，偶尔漏检。

**原因：ShuffleNetV2 的 channel shuffle 操作（reshape→transpose→reshape）在 onnx2tf 的 NCHW→NHWC 转换中被错误处理。**

### 第四回合：各种转换器逐个尝试

| 工具 | 结果 | 原因 |
|------|------|------|
| ai_edge_torch | ❌ | 依赖 `torch_xla`，无 Windows 版 |
| onnx-tf | ❌ | onnx 1.21 太新，`onnx.mapping` 被移除；降级后 `tensorflow_probability` 缺失 |
| onnx2keras | ❌ | 依赖冲突，API 变化 |
| onnx2tf 各种参数组合 | ❌ | INT8/INT16×8/per-tensor/input_only，全部精度全丢 |

### 第五回合：修改 ShuffleNetV2 来兼容

发现 channel shuffle 可以用 PyTorch 切片 `x[:,0::2,:,:]` 替代 `reshape→transpose→reshape`，数学上完全等价。在 ONNX 里变成 Slice 操作，不产生 Reshape。

修改后导出新 ONNX：
- Reshape：26 → 0 ✅
- Transpose：19 → 6 ✅
- Slice：0 → 26（替代了 channel shuffle）

ONNX Runtime 验证：和原始 ONNX 完全一致，diff=0.000000。

但拿去 onnx2tf 转——**仍然崩溃**。Slice 的 NCHW→NHWC 转换有 bug，depthwise conv 的通道数变成了 120≠48。

### 第六回合：认清现实

**onnx2tf 和 ShuffleNetV2 就是不兼容。不是某个参数的问题，是根本性的架构兼容问题。**

GD32 AI GUI 用的是 onnx2tf，所以整条 ONNX→GUI→TFLite 路线对 ShuffleNetV2 都行不通。

## 第五章：Keras 重写 — 终极方案

既然 ONNX→TFLite 的所有工具都不行，那就绕过 ONNX。

### 思路

```
PyTorch 权重 → Keras 重建模型 → TensorFlow 原生 TFLiteConverter → INT8 TFLite
```

TF 自己的工具对自己的 op 肯定不会有兼容性问题。

### 第一步：对照 PyTorch 源码逐层重建

仔细研读 PyTorch 源码：
- `shufflenetv2.py`：ShuffleV2Block（channel shuffle + branch_main + branch_proj）
- `fpn.py`：LightFPN（特征金字塔 + DWConv 细化块）
- `detector.py`：Detector 主类（backbone + FPN + 输出 Conv + sigmoid/softmax）

在 Keras 中逐一实现：
- 280 层，包括 Conv、DepthwiseConv、BatchNormalization、ReLU、MaxPool、ZeroPadding、Concatenate、UpSampling、Activation
- Channel shuffle 用 `x[:,:,:,0:C:2]` 实现（StridedSlice，TF 原生支持）
- 输出层复用 PyTorch 的共享 Conv 模式（同一个 output_reg 处理两个 head）
- BN epsilon 设为 1e-5（匹配 PyTorch）
- Conv 用 `use_bias=False`（PyTorch 习惯把 bias 放 BN 里）

### 第二步：权重迁移 — 371 个张量的精确匹配

导出 PyTorch state_dict 到 `pt_weights.npz`（444 个张量，含 buffers）。

需要解决的问题：
- **Keras 功能 API 的拓扑重排**：`model.layers` 顺序不是代码编写顺序，而是计算图拓扑序。不能按顺序匹配，必须用名字映射。
- **NCHW→NHWC 转置**：Conv 权重 `[O,I,Kh,Kw]` → `[Kh,Kw,I,O]`，DepthwiseConv 权重 `[C,1,Kh,Kw]` → `[Kh,Kw,C,1]`
- **BN 参数**：PyTorch 的 `num_batches_tracked`（Keras 不需要，跳过 73 个）
- **输出层共享**：PyTorch 的 output_reg_layers 是一个 Conv 用于两个 head，Keras 也用同一个 layer 对象

编写名字映射表：
- `backbone.first_conv.0.weight` → `f_c`
- `backbone.stage2.0.branch_main.0.weight` → `s2_0_m1_c`
- `backbone.stage2.0.branch_proj.0.weight` → `s2_0_p_d`
- `fpn.cls_head_2.block.0.weight` → `h0c__d1`
- `fpn.reg_head_2.block.0.weight` → `h0r__d1`
- `output_reg_layers.weight` → `oreg`
- ...等等，覆盖所有 371 个 Keras 权重槽位

**结果：371/371 权重全部迁移成功，0 失败！**

### 第三步：TFLite Float32 导出

TF 原生 TFLiteConverter → 961KB。

和 Keras 原版对比：**diff=0.000001**。完美！

### 第四步：INT8 量化

用 500 张 CCPD 校准数据做 PTQ：
- 全 INT8（输入+输出+权重）：401KB，diff=0.098
- Hybrid（float32 输入+INT8 输出+权重）：401KB，diff 相同

### 第五步：检测验证

20 张随机 CCPD 图（8 个类别混合）：
- Float32 TFLite：20/20 检出
- INT8 TFLite：20/20 检出
- Float32 vs INT8 偏差：**<3px**
- Keras vs ONNX（参考）：偏差 2-16px

对比 plate-best-sim.tflite（偏差 15-40px），提升巨大。

### 第六步：最终模型

**`yolo_keras_int8.tflite`** — 401KB, INT8：
```
输入:  [1, 192, 192, 3] int8  scale=0.003922 zp=-128
输出0: [1, 12, 12, 16]  int8  scale=0.003922 zp=-128 (stride=16)
输出1: [1, 6,  6,  16]  int8  scale=0.003922 zp=-128 (stride=32)
```

接口和 `plate-best-sim.tflite` **完全一致**，可以直接替换 Keil 工程里的模型。

## 第六章：C 代码修正

基于前面的分析，修正 `yolo_postprocess.c` 和 `yolo_postprocess.h`：

1. Anchor 数从 2 改为 **3**
2. 去掉多余的 sigmoid（模型输出已自带了）
3. 用正确 K-means anchors
4. 修正 channel 读取布局（reg[a*4..a*4+3] + obj[12+a] + cls[15]）
5. 修正 scale/zp（0.003922, -128）
6. 增加长宽比过滤（1.5~6.0）
7. 更新 main.c 调用（新的函数签名 + 正确的 scale/zp）

## 第七章：MCU 实测

### YOLO — 成功！

队友在 GD32H759I 上跑通，正确打框。这是第一次 MCU 实测成功的消息：

> "第一个模型跑成功了，可以打框了！！！"

### LPRNet — PC 验证通过，MCU 调试中

PC 端对 `input_data2_gray.pgm`（24×94 灰度图）跑 LPRNet INT8：
- 输出：**皖QA9588** ✅
- 三个模型（PyTorch/Float32 TFLite/INT8 TFLite）输出完全一致

MCU 上 LPRNet 结果不对，正在排查。初步推断是**输出反量化参数用错了**：
- LPRNet 输出 scale=0.2652, zp=-18
- YOLO 输出 scale=0.003922, zp=-128
- 两个不一样！如果 MCU 上 LPRNet 解码复用了 YOLO 的参数，结果就会错

### 省份显示为 `?`

不是模型问题——PC 端 pos0 省份置信度最高（26.3 分），argmax 正确指向"皖"。MCU 串口控制台可能不支持中文编码。

三模一致（PyTorch=TFLite Float32=TFLite INT8），LPRNet 模型本身没问题。

## 第九章：走过的弯路和教训

### 最惨烈的弯路：onnx2tf

花了大量时间在各种 onnx2tf 尝试上——改参数、改模型架构、换工具。从 float32 到 INT8 到 INT16×8，从原版到 Slice 版，全部失败。

**教训：onnx2tf 对包含复杂 reshape 的轻量网络（ShuffleNet、MobileNet）不支持。一旦发现，应该立刻放弃。**

### 最被低估的方案：Keras 重写

最初觉得"手动实现 280 层太麻烦"，结果反而是唯一成功的路线。花在 onnx2tf 上的时间足够重写 3 遍 Keras 了。

**教训：如果有复杂网络架构需要部署到 TFLite，最可靠的方法是在 TF/Keras 里重写并用 TF 原生工具转换。不要依赖第三方 ONNX→TFLite 工具。**

### 环境管理

- `yolo-fastest`: torch 2.6 + TF 2.21（训练）
- `tf-convert`: torch 2.6 + TF 2.13（TFLite 转换）
- ai_edge_torch 安装会降级 torch，破坏环境。Windows 上不能用。
- onnx 1.21 和 onnx-tf 不兼容。

### 最容易被忽略的细节

- BN epsilon：PyTorch 1e-5 vs Keras 1e-3。这 100 倍的差距会导致输出完全错误。
- 输出 scale/zp 每个模型不一样。YOLO 和 LPRNet 的输出量化参数不同，MCU 上必须分别处理。
- Keras functional API 的拓扑排序：layer 顺序不等于代码顺序，权重迁移不能用"第 N 个"来定位。
